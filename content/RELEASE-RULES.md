# 内容版本发布规则

## 铁律

**同一个版本号，只对应一次完整发布。**

- 内容改到一半时**不许**升版本号
- 升版本号 = 「这批改动已全部上线并验证」的信号
- 一次发布 = 一个版本号，中间不管改了多少文件

## 正确流程

```
1. 改内容（lessons/*.json、manifest.json 的 tree）
      ↓  manifest 的 version 保持不动
2. 本地验证
      ↓  所有 lesson 能解析、LaTeX 花括号平衡、题目答案验算
3. 上传全部文件到服务器
      ↓  一次性传完，不要分批
4. 逐个 curl 确认线上内容正确
      ↓  /lesson?id=... 每个改动过的节都拉一遍
5. 最后才改 manifest 的 version 和 updated
      ↓  这是「发布完成」的标记
6. 上传 manifest.json
      ↓  客户端这时才会感知到新版本
```

## 为什么

客户端（App / 网页版）靠 `manifest.version` 判断是否要刷新内容。如果版本号先升了但内容还没传完：

- 用户拉到新 manifest，看到新节目标题
- 点击进去却 404 或者内容是旧的
- 缓存里存下了残缺版本

**版本号是原子发布的提交点，不是「开始改」的标记。**

## 自查清单

发布前逐条确认：

- [ ] manifest `version` 还是旧值（没提前改）
- [ ] 所有新增/修改的 lesson json 已上传
- [ ] `curl /lesson?id=<每个改动过的节>` 全部 200 且有内容
- [ ] 新增的节已在 manifest `tree` 里（否则用户看不见）
- [ ] 删掉的节已从 `tree` 里移除（否则点进去 404）
- [ ] 所有题目答案经过验算
- [ ] LaTeX 花括号平衡（`{` 数 == `}` 数，排除 `\{` `\}`）
- [ ] commit message 里写清版本号和改了什么

## 发布后

- 线上抽查：至少拉一个新增节、一个修改节
- 记录：`git tag` 或者 commit message 里写 `v11`
- 若发现残缺：**立刻回滚 manifest 到上一版**，修好再升

## 历史教训

**v11（2026-11-19）**：先升了 manifest version=11，但 5.1 的八大性质只写完一半、8 个作业册节还没传完，导致用户拿到残缺版本。

纠正：内容是完整的（已复查 75 节点全部正常），但发布顺序错了。以后按上面的流程走。
